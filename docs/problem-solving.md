## 검색이 제목을 못 찾는다

`문제`  
벡터 검색을 붙였더니 엉뚱한 문제가 생겼다. "인터스텔라" 를 쳐도 1등이 아니었고
(1위 네트, 2위 인터스텔라), "크리스토퍼 놀란" 같은 이름은 아예 못 찾았다
(다크 크리스탈, 크리스마스… 글자만 비슷한 것들이 나왔다).

`원인`  
벡터는 의미가 가까운 걸 찾을 뿐 글자를 맞추지 못한다. "놀란" 이라는 이름은 임베딩
공간에서 또렷한 좌표가 아니라 주변 단어에 희석되어 버린다. 정확 매칭이 할 일을 벡터에
떠넘긴 꼴이었다.

`해결`  
둘을 합쳤다. 제목·감독·배우는 SQL 정확 매칭(`LIKE`)으로 잡아 위에 놓고,
분위기·내용은 벡터로 찾아 그 아래에 붙인다. 어느 쪽이 걸렸는지에 따라 RAG 코멘트도
갈랐다. 자연어 질의처럼 정확 매칭이 없을 때만 LLM 한 줄을 얹고, 제목·이름으로 찾을 때는
어색하니 붙이지 않는다.

## 추천이 인기순과 다를 게 없다

`문제`  
카탈로그가 4,894편인데 추천에 실제로 나오는 건 199편(4%)뿐이었다. 200명에게
거의 같은 목록을 주고 있었던 셈이다.

`원인`  
파고들어 보니 이웃 점수가 사실상 인기순이었다. 상위 100편을 좋아요 수와 나란히
놓으니 점수 순서와 인기 순서가 83.5%나 일치했다. `signal = Σ 자카드 가중치` 라 그 작품을
좋아한 이웃이 많을수록 점수가 커지는 구조였고, 결국 인기가 곧 점수였다.

`해결`  
넓혀 보려고 세 번 헛짚었다. 가중치를 조정하고, 순위로 결합(RRF)하고, 자리를
떼어 봤지만 전부 "후보를 더 넣자" 는 발상이었고 같은 벽에 부딪혔다. 답은 넣는 게 아니라
점수를 고치는 쪽이었다. 좋아요 수로 나눴다. 모두가 좋아하는 작품으로는 취향이 갈리지
않는다. 남들이 잘 안 보는 작품을 나와 겹쳐 좋아할 때 갈린다. 그게 핵심이었다.

```
              전     후
Recall@10    0.149  0.190
커버리지      199편  460편
```

정확도와 커버리지가 함께 올랐다. 넓히려던 세 시도마다 전후를 재 둔 덕에, 막힌 곳이
후보 수가 아니라 점수 계산이라는 게 드러났다.

## 테스트가 못 잡은 버그 — 도서 추천이 무작위가 될 뻔

`문제`  
영화 검색을 개선하려고 내용 점수 가중치를 0으로 내렸다. 영화 테스트도 벤치도 다
통과했다. 그런데 이대로 두면 도서 추천이 통째로 망가진다.

`원인`  
책은 시드 평점이 0건이라 이웃 점수가 전부 0이고, 내용 점수 하나로만 돌아간다.
가중치를 전역으로 0으로 만들면 모든 책의 점수가 0이 되어 순서가 무작위가 되는 것이다.
영화만 재는 벤치·테스트에서는 이게 보일 리 없었다.

```sql
select c.type, count(*) from user_contents uc join contents c on c.id = uc.content_id group by 1;
-- MOVIE 86,666
-- BOOK 0        ← 책은 이웃 신호가 없다
```

`해결`  
가중치를 매체별로 나눠, 영화는 이웃 점수만 쓰고 책은 내용 점수만 쓰게 했다.

같은 변경이 엉뚱한 곳도 건드렸다. 신작 자리 점수가 `가중치 × 유사도` 였는데, 영화 가중치가
0이 되니 신작 점수가 전부 0이 되어 정렬이 깨졌다. 코드를 훑다 발견해 내용 점수를 그대로
쓰게 고쳤다. 상수 하나가 쓰이는 곳이 세 군데였다.

## 100만 행 적재 — 파라미터 한도와 중복 키

`문제`  
시드 100만 건을 넣는데 배치 INSERT 가 실패했다.

```
sqlalchemy.exc.OperationalError: number of parameters must be between 0 and 65535
```

`원인`  
배치 10,000행에 컬럼이 7개니 70,000 파라미터, Postgres 프로토콜 한도(65,535)를
넘긴 것이다. 기존 스크립트는 5,000행이라 안 걸렸는데 100만 행을 넣느라 배치를 키우다 부딪혔다.

`해결`  
`COPY` 로 바꿨다. 파라미터 바인딩이 없으니 이 한도도 없다.

```python
with raw.cursor().copy(COPY_SQL) as copy:
    copy.write_row((...))
```

그런데 `COPY` 에는 `ON CONFLICT` 가 없어서 이번엔 중복 키에서 멈췄다.

```
psycopg.errors.UniqueViolation: duplicate key ... "user_contents_pkey"
```

`links.csv` 가 서로 다른 movieId 를 같은 tmdbId 로 보내다 보니, 한 유저가 같은 작품을 두 번
평가한 꼴이 됐다. 기존 INSERT 에서는 `on_conflict_do_nothing` 이 조용히 흡수하던 문제였다.
파이썬에서 `(userId, content_id)` 집합으로 미리 걸러 냈다. 997,423 → 997,416건, 7건 차이였다.

## 저장형 XSS (라이브 점검)

`문제`  
배포 전 보안 점검에서, 공개 메모에 `<script>alert(document.cookie)</script>` 를
넣어 봤더니 API 가 그대로 저장하고 되돌려 주었다. 자동 검사라면 여기서 취약이라 찍었을 것이다.

`원인`  
코드만 보고 판단하지 않고 실제 브라우저로 렌더를 확인했다. React 가 텍스트 노드로
이스케이프해 화면에는 글자로 보일 뿐 실행되지 않았다. 오탐이었고, 지금은 안전하다.

`해결`  
다만 방어가 프론트 한 겹뿐이라 모바일이나 서드파티 클라이언트가 붙으면 뚫린다.
그래서 저장 전에 태그를 걷어내는 겹을 하나 더 뒀다. 이스케이프가 아니라 제거인 이유는,
React 가 한 번 더 이스케이프하면 이중 이스케이프가 나서다. 태그가 아닌 꺾쇠(`a < b`)는
건드리지 않는다.

인증·JWT 위조·SQL 인젝션·유저 격리·로그인 잠금은 라이브에 직접 쳐 봤고 이미 막혀 있었다.
