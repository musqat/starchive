## 배포하자 모든 API가 500을 뱉었다

`문제`  
배포하자 모든 API가 500을 뱉었다. 바로 전까지 로컬 테스트 133개는 전부 통과한 상태였다.

`원인`  
재시도 라이브러리 `tenacity` 였다. 이 패키지가 수집 전용 의존성 그룹(`etl`)에
들어 있었는데, 처음엔 스크립트만 쓰던 코드를 LLM 재랭킹이 `reranker → pipeline →
router → main` 으로 끌어들이면서 런타임 의존이 되어 버렸다. Vercel 은 배포할 때
`[project].dependencies` 만 설치하고 `etl` 그룹은 건너뛴다. 로컬은 `uv sync --all-groups`
로 전부 깔려 있으니 이 구멍이 안 보였다.

`해결`  
`tenacity` 를 런타임 의존성으로 옮겼다. 그리고 같은 일이 반복되지 않도록,
배포 환경을 흉내 내서 `app/` 이 그룹 패키지를 건드리는지 미리 잡는 검증을 넣었다.

```bash
uv run --no-dev --no-group etl python -c "from app.main import app"
```

`app/` 에 새 import 를 넣을 때마다 이걸 돌린다. 로컬에서 통과해도 배포는 죽을 수 있다는
걸 검증 항목으로 박아 둔 셈이다. 나중에 CI 를 넣으면서 이 검증도 함께 넣었다.

## CI 를 넣자마자 세 개가 걸렸다

`문제`  
테스트 144개와 타입·린트를 손으로 돌리고 있었다. 위의 배포 의존성 검증도 마찬가지였다.
잊으면 그만이라 워크플로로 옮겼는데, 첫 실행부터 세 번 연달아 빨갛게 떴다.

`원인`  
셋 다 "로컬에는 있고 CI 에는 없는 것" 이었다.

```
1  설정값        Settings() 를 import 시점에 읽는다. .env 가 없으니
                DB 를 안 쓰는 테스트도 뜨지 못했다
2  라우트 타입    LayoutProps 는 next 가 빌드 때 .next/types 에 만든다.
                tsc 만 돌리면 없는 이름이다
3  시드 데이터    MovieLens csv 는 내려받는 것이라 저장소에 없다
```

세 번째를 고치다 진짜 버그가 하나 나왔다. `DIRECT_URL` 은 선택값(`str | None`)인데
수집 모듈이 그대로 `create_engine` 에 넘기고 있었다.

```python
engine = create_engine(settings.DIRECT_URL)   # None 이면 여기서 터진다
```

같은 파일 아래쪽은 이미 `settings.DIRECT_URL or settings.DATABASE_URL` 로 폴백하는데
이 줄만 빠져 있었다. 로컬 `.env` 에는 둘 다 적혀 있어 한 번도 드러나지 않았다.
`DIRECT_URL` 없이 배포하면 수집 모듈은 import 조차 안 된다.

`해결`  
설정값은 워크플로에 넣고, 프론트는 빌드를 먼저 돌린다. 시드 데이터는 파일이 없으면
건너뛴다 — `external` 마커는 외부 API 호출을 뜻해 맞지 않았다. `DIRECT_URL` 은
`DATABASE_URL` 로 폴백한다.

CI 가 처음 한 일이 자기를 넣은 이유를 증명한 셈이다. 셋 다 로컬에서는 문제 없었다.

## 전송량 초과로 18일 다운

`문제`  
어느 날 갑자기 모든 DB 요청이 실패했다. 목록·상세·로그인·추천이 전부 500이고,
DB 를 안 쓰는 `/health` 와 `/docs` 만 응답했다.

```
psycopg.OperationalError: Your project has exceeded the data transfer quota.
```

`원인`  
무료 티어의 월 전송량 5GB 를 넘긴 것이었다. 저장 용량은 0.12/0.5GB 로 넉넉했는데,
그쪽만 신경 쓰는 사이 전송량 벽에 부딪혔다. 따라가 보니 취향 중심을 만들 때 임베딩을
파이썬으로 끌어와 평균을 내고 있었다. 유저 한 명당 1536차원 벡터 수십 개, 평가 한 번에
수백 MB 가 오갔다. 그걸 프로덕션에 대고 열 번 넘게 돌렸으니 쿼터가 남을 리 없었다.

`해결`  
세 가지로 손봤다.

```
1  평균을 Postgres 로 내린다     벡터 수십 개 대신 결과 하나만 오간다. 지표는 그대로
2  평가용 로컬 DB (도커)          평가 전송량이 0
3  가드                          평가가 원격을 향하면 연결 전에 멈춘다
```

배치 추천도 같은 경로를 타던 터라 프로덕션 전송량까지 함께 줄었다. 서비스는 Neon 에서
Supabase 로 옮겨 복구했고, 카탈로그는 로컬에서 다시 만들어 올렸다. 핵심은 막을 수 없는
실수를 싸게 실패하도록 바꾼 것이다. 이제 원격에 평가를 돌리면 3초 만에 멈추면서 무엇을
해야 하는지 알려 준다.

## 추천이 인기순과 다를 게 없다

`문제`  
카탈로그가 4,894편인데 추천에 실제로 나오는 건 199편(4%)뿐이었다. 200명에게
거의 같은 목록을 주고 있었던 셈이다.

`원인`  
파고들어 보니 이웃 점수가 사실상 인기순이었다. 상위 100편을 좋아요 수와 나란히
놓으니 점수 순서와 인기 순서가 83.5%나 일치했다. `signal = Σ 자카드 가중치` 라 그 작품을
좋아한 이웃이 많을수록 점수가 커지는 구조였고, 결국 인기가 곧 점수였다.

`해결`  
넓혀 보려고 세 번 헛짚었다. 가중치를 조정하고, 순위로 결합(RRF)하고, 자리를
떼어 봤지만 전부 "후보를 더 넣자" 는 발상이었고 같은 벽에 부딪혔다. 답은 넣는 게 아니라
점수를 고치는 쪽이었다. 좋아요 수로 나눴다. 모두가 좋아하는 작품은 내 취향을 알려주지
않는다. 남들이 잘 안 보는 작품을 나와 겹쳐 좋아한다는 것, 그게 신호다.

```
              전     후
Recall@10    0.149  0.190
커버리지      199편  460편
```

정확도와 커버리지가 함께 올랐다. 막힌 곳을 무작정 넓히기 전에 어디가 막혔는지부터
잰 것이 방법을 찾아 주었다.

## 검색이 제목을 못 찾는다

`문제`  
벡터 검색을 붙였더니 엉뚱한 문제가 생겼다. "인터스텔라" 를 쳐도 1등이 아니었고
(1위 네트, 2위 인터스텔라), "크리스토퍼 놀란" 같은 이름은 아예 못 찾았다
(다크 크리스탈, 크리스마스… 글자만 비슷한 것들이 나왔다).

`원인`  
벡터는 의미가 가까운 걸 찾을 뿐 글자를 맞추지 못한다. "놀란" 이라는 이름은 임베딩
공간에서 또렷한 좌표가 아니라 주변 단어에 희석되어 버린다. 정확 매칭이 할 일을 벡터에
떠넘긴 꼴이었다.

`해결`  
둘을 합쳤다. 제목·감독·배우는 SQL 정확 매칭(`LIKE`)으로 잡아 위에 놓고,
분위기·내용은 벡터로 찾아 그 아래에 붙인다. 어느 쪽이 걸렸는지에 따라 RAG 코멘트도
갈랐다. 자연어 질의처럼 정확 매칭이 없을 때만 LLM 한 줄을 얹고, 제목·이름으로 찾을 때는
어색하니 붙이지 않는다.

## 저장형 XSS (라이브 점검)

`문제`  
배포 전 보안 점검에서, 공개 메모에 `<script>alert(document.cookie)</script>` 를
넣어 봤더니 API 가 그대로 저장하고 되돌려 주었다. 자동 검사라면 여기서 취약이라 찍었을 것이다.

`원인`  
코드만 보고 판단하지 않고 실제 브라우저로 렌더를 확인했다. React 가 텍스트 노드로
이스케이프해 화면에는 글자로 보일 뿐 실행되지 않았다. 오탐이었고, 지금은 안전하다.

`해결`  
다만 방어가 프론트 한 겹뿐이라 모바일이나 서드파티 클라이언트가 붙으면 뚫린다.
그래서 저장 전에 태그를 걷어내는 겹을 하나 더 뒀다. 이스케이프가 아니라 제거인 이유는,
React 가 한 번 더 이스케이프하면 이중 이스케이프가 나서다. 태그가 아닌 꺾쇠(`a < b`)는
건드리지 않는다.

인증·JWT 위조·SQL 인젝션·유저 격리·로그인 잠금은 라이브에 직접 쳐 봤고 이미 막혀 있었다.

## 테스트가 못 잡은 버그 — 도서 추천이 무작위가 될 뻔

`문제`  
영화 검색을 개선하려고 내용 점수 가중치를 0으로 내렸다. 영화 테스트도 벤치도 다
통과했다. 그런데 이대로 두면 도서 추천이 통째로 망가진다.

`원인`  
책은 시드 평점이 0건이라 이웃 점수가 전부 0이고, 내용 점수 하나로만 돌아간다.
가중치를 전역으로 0으로 만들면 모든 책의 점수가 0이 되어 순서가 무작위가 되는 것이다.
영화만 재는 벤치·테스트에서는 이게 보일 리 없었다.

```sql
select c.type, count(*) from user_contents uc join contents c on c.id = uc.content_id group by 1;
-- MOVIE 86,666
-- BOOK 0        ← 책은 이웃 신호가 없다
```

`해결`  
가중치를 매체별로 나눠, 영화는 이웃 점수만 쓰고 책은 내용 점수만 쓰게 했다.

같은 변경이 엉뚱한 곳도 건드렸다. 신작 자리 점수가 `가중치 × 유사도` 였는데, 영화 가중치가
0이 되니 신작 점수가 전부 0이 되어 정렬이 깨졌다. 코드를 훑다 발견해 내용 점수를 그대로
쓰게 고쳤다. 상수 하나를 바꾸면 그 상수가 쓰이는 모든 곳을 따라가야 한다는 걸 다시 배웠다.

## 100만 행 적재 — 파라미터 한도와 중복 키

`문제`  
시드 100만 건을 넣는데 배치 INSERT 가 터졌다.

```
sqlalchemy.exc.OperationalError: number of parameters must be between 0 and 65535
```

`원인`  
배치 10,000행에 컬럼이 7개니 70,000 파라미터, Postgres 프로토콜 한도(65,535)를
넘긴 것이다. 기존 스크립트는 5,000행이라 안 걸렸는데 100만 행을 넣느라 배치를 키우다 부딪혔다.

`해결`  
`COPY` 로 바꿨다. 파라미터 바인딩이 없으니 이 한도도 없다.

```python
with raw.cursor().copy(COPY_SQL) as copy:
    copy.write_row((...))
```

그런데 `COPY` 에는 `ON CONFLICT` 가 없어서 이번엔 중복 키로 터졌다.

```
psycopg.errors.UniqueViolation: duplicate key ... "user_contents_pkey"
```

`links.csv` 가 서로 다른 movieId 를 같은 tmdbId 로 보내다 보니, 한 유저가 같은 작품을 두 번
평가한 꼴이 됐다. 기존 INSERT 에서는 `on_conflict_do_nothing` 이 조용히 흡수하던 문제였다.
파이썬에서 `(userId, content_id)` 집합으로 미리 걸러 냈다. 997,423 → 997,416건, 7건 차이였다.

## 마이그레이션 자동 생성이 놓치는 것들

`문제`  
Alembic 의 `autogenerate` 를 믿고 그대로 올렸다가 같은 함정을 반복해서 밟았다.

`원인`  
`nullable=False` 컬럼을 추가하면 기존 행에 채울 기본값(`server_default`)이 있어야
하는데, 자동 생성은 그걸 안 넣어 준다. 그대로 올리면 기존 데이터에서 실패한다.
`token_version`, `failed_logins` 같은 컬럼에서 네 번쯤 겪었다. enum 타입은 반대로 중복해서
만든다. 이미 있는 `content_type` 에도 `CREATE TYPE` 을 다시 찍어 `type already exists` 가 났다.

`해결`  
`create_type=False` 로 enum 중복을 막고, `server_default` 는 손으로 채워 넣었다.
결국 교훈은 하나다. `revision --autogenerate` 로 만든 파일은 읽고 손봐야 한다. 인덱스도
놓치고 위의 둘도 놓친다. 도구가 초안까지는 주지만 검토는 사람 몫이다.

<br>

## 벤치마크가 거짓 결론을 냈다

측정으로 판단하는 프로젝트라, 벤치 자체의 버그가 무엇보다 위험했다.

`문제`  
한번은 신작 자리를 재는데 1칸(0.154)이 0칸(0.149)보다 높게 나왔다. 정답이 될 수
없는 신작을 넣었는데 Recall 이 오르는 건 불가능한 일이다.

`원인`  
난수원 하나를 홀드아웃 뽑기와 신작 뽑기에 같이 써서, 설정마다 홀드아웃이 달라져
있었다. 또 작은 표본에 속을 뻔한 적도 있다. 질의 확장은 한 영화가 3위로 살아난 것만 보고,
색인 개선은 600편 실험의 +30%만 보고 채택할 뻔했다. 둘 다 전체로 다시 재니 손해거나 미미했다.

`해결`  
난수원은 둘로 갈랐다. 그리고 돌리기 전에 검산 기준을 정해 두는 습관을 들였다.
"0칸이 Recall 최댓값이어야 한다" 를 먼저 못 박아 두면 난수 버그가 그 자리에서 걸린다.
